# P0-015 性能PoCレビュー

版: 1.0
状態: 測定完了、現方式の正式採用は保留
基準日: 2026-08-02

## 1. 目的

P0-015で取得した1万文書・同時利用性能PoCの結果を分析し、現方式の採否、改善方針、追加PoC、P0-016以降の進行可否、およびP0-023までに満たす性能基準を整理する。

本資料はレビュー記録であり、現行PoCコードを製品実装へ昇格させる承認ではない。

## 2. 結論

- P0-015は「測定完了」として扱う。
- 候補一覧、ETag競合検知、索引整合性の測定結果は合格とする。
- 初回走査と検索は暫定基準未達であり、現方式の正式採用は保留する。
- P0-015の再実施は行わず、今回の値を改善前ベースラインとして保持する。
- 走査性能、FTS構成・検索性能、SQLite依存パッケージを別々の追加PoCで検証する。
- P0-016以降の独立したPoCは先行可能とする。
- 検索・索引方式の正式確定、およびP0-023の設計ゲート完了には追加PoCの完了を必須とする。

## 4. 初回走査のボトルネック

### 4.1 現在の測定内容

現在の`ScanCorpus`は、すべてのMarkdownを列挙し、各ファイルを開いて全内容のSHA-256を計算している。

このため、「初回走査」という一つの値に次の処理が混在している。

- ファイル列挙
- ファイル属性取得
- ファイルオープン
- 全内容の読み込み
- SHA-256計算

さらに、ウォームアップ3回の後に20回測定しているため、OSファイルキャッシュがない状態の厳密なコールド初回走査とは異なる。今回の5,141.1 msは、軽量な文書発見ではなく、約686 MBの全内容検証に近い測定値として解釈する。

索引作成前には全文書本文を`ReadAllText`で読み、配列としてメモリに保持している。この構造も約1.9 GBのピークワーキングセットに影響している可能性が高い。

### 4.2 推奨する走査パイプライン

正式構成では、次の段階へ分離する。

1. パス、サイズ、更新日時による高速な文書発見
2. `.adm-meta`およびSQLiteキャッシュとの比較
3. 新規・変更候補の抽出
4. 候補ファイルだけの内容読み込み
5. 必要な場合だけハッシュ計算
6. バックグラウンドでの解析・索引更新

フルSHA-256は、更新日時またはサイズが変わった場合、ETag生成または競合確認、整合性監査など、内容確認が必要な場合に限定する。

### 4.3 次回測定で分離する値

- ファイル列挙時間
- 基本属性取得時間
- `.adm-meta`読取時間
- 差分候補抽出時間
- 本文読取時間
- ハッシュ計算時間
- Markdown解析時間
- 索引投入時間
- UIまたはAPIが利用可能になるまでの時間
- 全バックグラウンド処理が完了するまでの時間

## 5. 検索のボトルネック

### 5.1 測定クエリの特性

測定に使用した「ユーザー認証」は、生成コーパスのほぼ全文書に多数含まれる。そのため、945.2 msは大量ヒットする広域クエリの値である。

現在の検索クエリは、一度に次を実行する。

- FTS5の`MATCH`
- 多数候補に対するBM25順位計算
- 順位とパスによる並べ替え
- `snippet()`生成
- 上位件数の取得

大量ヒット時の順位計算、並べ替え、snippet生成が主な負荷候補である。

今回のP0-015は`unicode61`索引だけを使用している。したがって、今回の索引作成時間、容量、検索時間はunicode61／trigram併用方式の測定値ではない。

### 5.2 測定条件の改善

正式な性能評価では、検索語の選択度を分ける。

| クエリ区分 | 例・目的 |
|---|---|
| 低ヒット | まれな日本語、特定文書名 |
| 中ヒット | 一部のチケットや設計資料に現れる語 |
| 高ヒット | 全文書に近い一般語 |
| 識別子 | チケット番号、ULID、人が読める連番ID |
| エラーコード | 英数字、記号を含むコード |
| 部分一致 | 日本語の語中一致、ファイル名の一部 |
| 該当なし | 0件検索のオーバーヘッド確認 |
| 複合条件 | 文書種別、状態、プロジェクトなどとの併用 |

平均または一種類のp95だけでなく、標準検索と高ヒット検索を別基準で判定する。

## 6. unicode61／trigram方式の見直し

### 6.1 推奨案

MVPでは、unicode61とtrigramによる二つの全本文索引を常時保持しない。

- 通常検索は`unicode61`を基本とする。
- 日本語フレーズ、英数字、エラーコード、完全な識別子を通常検索で扱う。
- 部分一致は、利用者が明示的に選ぶ検索モードとして扱う。
- trigramを採用する場合は、ファイル名、見出し、人が読めるID、エラーコードなどの短い項目を優先する。
- 全本文trigramは、追加PoCでディスク容量、索引作成時間、更新時間、検索時間が正式基準を満たした場合だけ採用候補とする。

### 6.2 代替案

1. unicode61だけをMVPで採用し、任意位置の部分一致を将来機能にする。
2. unicode61で候補文書を絞り、少数の候補にだけアプリケーション側の部分一致を適用する。
3. 日本語形態素解析トークナイザーを導入する。

形態素解析方式は、追加ライブラリ、辞書、配布、更新、ネイティブ依存の管理が必要になる。MVPでは過剰設計となる可能性が高いため、現時点の推奨案にはしない。

## 7. 索引作成・検索クエリ・snippetの改善候補

### 7.1 本文の二重保存を減らす

現在は通常テーブルとFTSテーブルの双方に本文を保持しており、約686 MBのコーパスに対して約2.13 GBの出力となっている。

FTS5のexternal-content方式を比較候補とし、本文を通常テーブルに一度だけ保持してFTS索引から参照する。SQLite公式資料では、通常のFTS5テーブルが内容のコピーを保持すること、およびexternal-content/contentless構成で重複を減らせることが説明されている。

ただし、external-content方式では通常テーブルとFTS索引の同期責任がアプリケーション側に増える。トランザクション、再構築、`integrity-check`、異常終了回復を追加PoCで検証する。

### 7.2 snippetを上位候補だけに生成する

検索を二段階に分ける。

1. `rowid`、順位、必要最小限の表示情報だけで上位候補を取得する。
2. 上位20～50件だけにsnippetを生成する。

これにより、上位結果に残らない大量の候補へsnippet処理を行うことを避ける。

### 7.3 snippet対象列を修正する

現状の`snippet(documents_fts, 3, ...)`は、FTS列定義上`heading`を指定している。本文は列4である。

正式実装では次を比較する。

- 本文列4を明示する。
- 列番号へ負数を指定し、FTS5へ最適列の選択を任せる。
- 見出し用snippetと本文用snippetを用途別に生成する。

### 7.4 索引対象列を限定する

`status`、関連ID、パスなど構造化条件で扱える項目は、通常列または`UNINDEXED`列として扱う。全文検索が必要な見出し、本文、ファイル名などへFTS索引を限定する。

### 7.5 一括索引作成を効率化する

- 一つのトランザクション内でprepared commandを再利用する。
- 文書ごとのSQLコマンド再生成とパラメーター再構築を減らす。
- 全文書を配列に保持せず、ストリーミングまたは制限付きバッチで投入する。
- キャッシュは再構築可能であるため、`journal_mode`、`synchronous`、キャッシュサイズなどを安全性要件の範囲で比較する。
- 全再構築後のFTS5 `optimize`を測定する。ただし、通常の文書更新ごとには実行しない。

### 7.6 順位計算を比較する

次のクエリを同じデータと検索語で比較する。

- 現在の`bm25()`呼び出し
- FTS5の`rank`列
- 構造化条件で対象を絞ってからの全文検索
- 上位候補取得とsnippet生成を分ける二段階検索

## 8. SQLite依存パッケージの安全性

### 8.1 現状

PoCは`Microsoft.Data.Sqlite 10.0.10`を直接参照し、推移依存として`SQLitePCLRaw.lib.e_sqlite3 2.1.11`を使用している。

NU1903の2件は、異なる二つの脆弱性ではなく、同じ推移依存が複数のPoCプロジェクトで検出されているものと判断する。GitHub Advisory `GHSA-2m69-gcr7-jv3q`では、SQLite 3.50.2より前に関係する問題として、`SQLitePCLRaw.lib.e_sqlite3` 2.1.11以下が影響対象になっている。

### 8.2 推奨する更新候補

追加PoCの第一候補は次の組み合わせとする。

- `Microsoft.Data.Sqlite.Core 10.0.10`
- `SQLitePCLRaw.bundle_e_sqlite3` 3.xを明示参照
- 検証開始時点の候補バージョン: 3.0.5

Microsoftの公式資料でも、既定以外のSQLiteバンドルを使用する場合は`Microsoft.Data.Sqlite.Core`と目的のSQLitePCLRawバンドルを組み合わせる方法が示されている。

この組み合わせは検証候補であり、PoC完了前に正式採用しない。

### 8.3 必須検証

- リポジトリ直下の`global.json`で固定した.NET SDK 10.0.302を使用する。
- `dotnet --version`の実測値をPoC結果に記録する。
- restore、Debug/Release buildが成功する。
- Framework-dependentおよび必要な`win-x64`配布形態を確認する。
- `select sqlite_version()`で実際のSQLiteバージョンを記録する。
- FTS5が有効で、P0-014の検索契約を維持する。
- NU1903を含むHigh/Criticalの既知脆弱性警告を0件にする。
- 配布物に含まれるネイティブDLLとロード対象を確認する。
- Windows Service、コンソール、WPFから共通の構成で利用できることを確認する。
- ライセンス、依存バージョン固定、SBOM出力を確認する。

Windows付属SQLiteへ切り替える案は、SQLiteバージョンとFTS5機能を製品側で統制しにくいため推奨しない。

## 10. P0-016以降の進行可否

P0-016はLAN HTTPS初期設定に関する別領域のPoCであり、P0-024～P0-026に依存しないため先行可能とする。

P0-017以降も次の条件を守る限り、依存関係に従って進行できる。

- 現在のSQLite検索実装を正式方式として固定しない。
- UI PoCは検索APIの仮契約またはモックを使用できる。
- UIおよびAPI契約を現行PoCの内部実装へ密結合させない。
- Phase 1の正式検索実装はP0-025の採用判断後に開始する。
- P0-023はP0-024～P0-026の結果を確認してから完了判定する。

性能改善PoCはPhase 0全体を停止する直列ブロッカーではなく、P0-023の必須前提として扱う。

## 11. P0-023までに満たす正式性能基準

次の値をP0-023の設計確定ゲートにおける推奨基準とする。測定対象は1万文書、同時利用者5名、AIクライアント2接続の基準環境とする。

| 項目 | 推奨基準 |
|---|---:|
| 有効なキャッシュがあるServer起動 | p95 3秒以内 |
| 10,000件のパス・基本属性発見 | p95 3秒以内 |
| 変更なし再走査 | p95 2秒以内 |
| 1文書変更の検出・索引反映 | p95 2秒以内 |
| 初回全文走査＋索引完成 | 60秒以内、UIをブロックしない |
| 候補一覧API | p95 500 ms以内 |
| 標準的な検索の先頭ページ | p95 500 ms以内 |
| 大量ヒットする広域検索 | p95 1,000 ms以内 |
| 検索取消 | 取消操作後2秒以内に処理終了 |
| 通常稼働時メモリ | 512 MiB以下を目標 |
| 全索引再構築時ピークメモリ | 1 GiB以下 |
| SQLiteキャッシュ容量 | 検索対象本文量の1.5倍以下を目標 |
| ETag競合検出 | 競合の見逃し0件 |
| 索引整合性 | 欠落、重複、旧版混入0件 |
| パッケージ安全性 | High/Critical既知脆弱性0件、NU1903 0件 |
| 障害時回復 | SQLiteキャッシュを破棄し、Markdownと`.adm-meta`から再構築可能 |

「標準的な検索」と「大量ヒットする広域検索」は別シナリオで測定する。今回の945.2 msは広域検索の推奨基準内だが、現方式の採用根拠にはしない。本文の二重保存、約1.9 GBのピークメモリ、約2.13 GBの出力容量、および依存パッケージ警告を追加PoCで解消または妥当化する必要がある。

## 12. P0-023の判定条件

P0-023では、少なくとも次をすべて確認する。

1. P0-024で走査パイプラインと増分走査方式が確定している。
2. P0-025でMVPのTokenizer、索引構成、snippet方式、検索クエリが確定している。
3. P0-026でSQLiteネイティブ依存と既知脆弱性への対応が確定している。
4. 第11節の基準を満たすか、未達値について利用者影響、代替策、Phase 1対応が明示されている。
5. 正確性、競合検知、索引整合性を犠牲にする性能改善を採用していない。
6. 採用判断と不採用案がADRへ記録されている。
