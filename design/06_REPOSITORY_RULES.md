# AI Development Manager リポジトリ規約

版: 1.0
状態: Phase 0 P0-001確定
基準日: 2026-08-02

## 1. 目的と適用範囲

この規約は、実装開始後に配置、命名、Build番号、チケットの完了条件が揺れないようにするための共通ルールである。開発者、AIエージェント、レビュー担当者に適用する。

優先順位は、ユーザーの明示指示、対象チケット、`design/`の設計・ADR、本規約、実装者の判断の順とする。矛盾がある場合は上位の資料を優先し、必要ならチケットまたはADRを更新する。

## 2. リポジトリ構成

| パス | 責務 | 置いてよいもの | 置かないもの |
|---|---|---|---|
| `src/` | 製品コード | Server、WPF、Web UI、共通ライブラリ | PoC専用コード、テストコード |
| `tests/` | 製品コードの自動テスト | Unit、Integration、UI、Regressionテスト | 実データ、手動確認の結果 |
| `poc/` | 技術検証 | 独立した検証コード、入力、実行手順 | 製品コードへの自動昇格、秘密情報 |
| `design/` | 設計・ADR・規約 | 基本設計、API方針、判断記録、測定基準 | 実行時データ、ビルド生成物 |
| `tickets/` | 作業計画と完了記録 | チケット、結果、証拠へのリンク | 製品実装、秘密情報 |
| `output/` | 人が確認する成果物 | 生成PDF、画面キャプチャ、レポート | 正本データ、キャッシュ、認証情報 |

`output/`に置く生成物は、レビューや引き渡しに必要な小容量の成果物だけを追跡対象とする。再生成できる中間生成物は追跡しない。

予定構成は、ソリューションをルートに置き、製品プロジェクトを`src/`、テストプロジェクトを`tests/`、PoCを`poc/`に配置する。Phase 0ではこの予定構成の規約確定までとし、製品プロジェクトの作成は後続チケットで行う。

## 3. 命名とチケット分割

- チケット番号は`P<phase>-<3桁>`、例: `P0-001`とする。Build番号とは別物である。
- 新規設計資料は既存の連番と責務を確認し、`design/NN_<PURPOSE>.md`形式を基本とする。
- 1チケットは、単独で実施、レビュー、結果確認、完了判定できる1つの変更目的に限定する。
- UI基盤変更と画面機能変更、データ形式変更と移行処理、API契約変更と利用画面変更は分離する。
- 依存関係がある場合は、先行チケットを完了してから後続チケットに着手する。PoCの合否に依存する採用判断はADRに残す。

### 変更分割の判定例

| 変更内容 | チケットの扱い |
|---|---|
| ASP.NET CoreのHost骨格を作る | Server基盤チケット1件 |
| Server骨格に認証機能を追加する | 認証機能チケットへ分離 |
| Reactの採否を比較検証する | Web UI技術PoC 1件。製品UI実装は別チケット |
| Markdownスキーマを決めて既存データを変換する | スキーマ決定と移行処理を分離 |
| 共通Themeを作り、画面に適用する | UI基盤変更と画面変更を分離 |
| APIの保存方式を変更し、バックアップを追加する | 保存方式変更とバックアップ変更を分離 |
| 既存文書を読み取り、索引を再構築する | 走査・判別と索引実装を依存チケットに分離 |

次の混在は完了条件を満たさない: 「基盤変更と複数機能の同時実装」「データ形式変更と無記録の一括移行」「画面変更とUI基盤刷新」「PoC結果を記録しないまま製品コードへ採用」。

## 4. ブランチ、コミット、レビュー

- 作業ブランチは`main`または既定の保護ブランチへ直接作業せず、`<type>/<ticket>-<short-description>`形式を基本とする。例: `docs/P0-001-repository-rules`。
- `<type>`は`feature`、`fix`、`docs`、`poc`、`test`、`chore`のいずれかとする。
- 1コミットはレビュー可能な論理単位とし、コミットメッセージは`<ticket>: <imperative summary>`形式とする。例: `P0-001: define repository rules`。
- フォーマットだけの変更、生成物、秘密情報を混ぜない。
- レビュー依頼には、変更ファイル、受入条件ごとの結果、テストコマンド、目視確認、既知の未解決事項を記載する。
- レビュー指摘を修正した場合は、再テストと差分確認を行う。

## 5. バージョンとBuild番号

Build番号の生成元は、リポジトリで管理する単一の`BuildNumber`値とする。将来の`.NET`実装では`Directory.Build.props`または同等の単一設定から各成果物へ渡し、プロジェクトごとに個別の番号を持たせない。

| 項目 | 規則 |
|---|---|
| Assembly Version | 互換性を壊す公開API変更時だけ更新する。通常の修正では固定する |
| File Version | 配布可能な成果物を作るたびに`major.minor.patch.build`へ反映する |
| Informational Version | `major.minor.patch+<commit-or-build-label>`を基本とし、検証可能なGitコミットまたはBuildラベルを含める |
| Build番号 | 単一の単調増加する整数。生成元は1つ、更新タイミングは成果物作成前の1回だけ |
| チケット番号 | 作業目的を識別する番号。Build番号の代用にしない |

例:

- 開発版: `Assembly 1.0.0.0`、`File 0.1.0.120`、`Informational 0.1.0-dev+abc1234`、`Build 120`
- 検証版: `Assembly 1.0.0.0`、`File 0.1.0.121`、`Informational 0.1.0-rc.1+build121`、`Build 121`
- 正式版: `Assembly 1.0.0.0`、`File 1.0.0.122`、`Informational 1.0.0+build122`、`Build 122`

Build番号は開発・検証・正式版を通して巻き戻さず、同じ番号を別の成果物へ再利用しない。コミット、成果物、テスト結果、リリース記録から追跡できるようにする。チケット番号は`P0-001`のままで、Build番号を更新するたびに変更しない。

## 6. 設計資料、テスト、実機確認

チケット完了には、次の順序を含める。

1. 実装または文書変更
2. 関連する設計資料・ADR・チケット状態の更新
3. 自動テスト、静的検査、または文書レビュー
4. 対象環境での実機・実アプリ確認。文書のみの場合はリンク、構成、表、コードブロックを実際に確認する
5. 差分、テスト結果、受入条件、未解決事項のレビュー

UI変更は、基準画像が指定されていればそれを最優先し、実際にアプリを起動して画面を確認する。PoCは合格・不合格の双方を記録し、採用判断をADRへ残す。

## 7. コミット除外規則

次のものはコミットしない。将来の`.gitignore`、`.editorconfig`、`Directory.Build.props`の設計・実装時にもこの一覧を反映する。

- 証明書、秘密鍵、`*.pfx`、`*.p12`、`*.key`、トークン、Cookie、接続文字列、`.env`などの秘密情報
- 実利用者の文書、添付、ログ、個人情報を含む実データ
- バックアップ、復元用スナップショット、作業用コピー
- SQLiteなどの索引キャッシュ、ローカルDB、実行時状態、ロックファイル
- `bin/`、`obj/`、`node_modules/`、テスト結果の一時フォルダー、カバレッジ中間生成物
- 大容量の生成PDF、動画、ZIP、画面録画、中間画像。レビュー用に必要な小容量成果物は`output/`へ明示的に配置する
- OS、IDE、ユーザー固有設定、秘密を含む診断ダンプ

サンプルデータは匿名化・最小化し、実データと明確に区別する。除外漏れが疑われる場合はコミットを止め、内容を確認してから追跡対象を決める。

## 8. P0-001の検証記録

### 変更分割レビュー

第3節の7例を確認し、基盤、機能、データ、移行、PoC、画面、バックアップ、索引の境界が一意に判断できることを確認する。

### Build番号レビュー

第5節の開発版`120`、検証版`121`、正式版`122`を時系列に確認し、生成元が単一で、重複・巻き戻しがなく、チケット番号と混同しないことを確認する。

### 除外対象レビュー

第7節に秘密情報、実データ、バックアップ、キャッシュ、ビルド生成物、大容量生成物が含まれることを確認する。
