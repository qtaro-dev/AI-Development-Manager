# P0-011 パス境界・リンク安全性PoC

## 目的

登録済みプロジェクトルート外への読取・書込を、パス表現やリンクを使って回避できないことを確認する。

## 前提・依存関係

- P0-003完了

## 対象範囲

- `..`、絶対パス、UNC、デバイスパス
- シンボリックリンク、ジャンクション
- NTFS代替データストリーム
- 大文字小文字、末尾ドット、予約名
- アップロード名の正規化

## 対象外

- ZIP内部パス
- ウイルススキャン製品の選定
- UNC／NAS正式対応

## 対象ファイルまたは対象モジュール

- `poc/path-security`
- 設計候補: `Adm.Storage.SafePath`

## 具体的な実装内容

1. 入力パスと実体パスの検証手順を作る。
2. 読取、書込、ダウンロード、アップロードで同じ境界規則を使う。
3. リンクを拒否する既定方針と検出限界を記録する。
4. 拒否理由を内部詳細と利用者向け文言へ分ける。

## テスト内容

- 代表的なパストラバーサル文字列
- URLエンコードと二重エンコード
- リンク経由のルート外参照
- ADS、予約名、末尾空白
- 正常な日本語ファイル名

## 受け入れ条件

- すべての危険ケースを拒否するか、制約を明記する。
- 正常なプロジェクト内ファイルを誤拒否しない。
- パス検証が一つの共通サービスへ集約される設計になる。

## ユーザーが目視確認する内容

- 許可・拒否ケース一覧。
- 利用者向けの分かりやすい拒否理由。

## 想定されるリスク

- Windowsパスの正規化差異。
- 権限変更やリンク差替えによる検査時と利用時の差。

## 完了後に更新すべき設計資料

- ファイル保護仕様
- 添付API仕様
- セキュリティ試験方針

## 実施結果

- 実施日: 2026-08-02
- 実装: `poc/path-security`
- SDK: .NET SDK 10.0.302（`dotnet --version`実測値: 10.0.302、Runtime: 10.0.10）
- 共通サービス: 読取、書込、ダウンロード、アップロードで同一検証を利用。
- 拒否: `..`、URL二重エンコード、絶対・UNC・デバイスパス、Reparse Point、ADS、予約名、末尾ドット・空白。
- 許可: プロジェクト内の通常パス、日本語ファイル名。
- アップロード名: ディレクトリ要素を拒否し、Unicode NFCへ正規化。
- 結果: 正常3件、危険10件、4操作共通検証、リンク拒否を確認。
- 制約: 検査後のリンク差替えは残余リスク。製品では安全なハンドル・ACL・再検証が必要。
- 判定: 合格。P0-012以降は未着手。

- Windows実機でのジャンクション、ADS、予約名の追加確認。
- 製品コードへの正式採用はP0-023で判断する。
